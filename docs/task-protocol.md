# Протокол ведения файлов состояния

Общий для всех агентов (Claude Code, Codex и любых следующих). Живёт в репозитории проекта.
`CLAUDE.md` и `AGENTS.md` только ссылаются сюда — правится один файл.

## Три файла, три горизонта

| файл | отвечает на вопрос | как часто меняется |
|---|---|---|
| `TASKS.md` | что делать | каждую сессию |
| `CONTEXT.md` | как всё устроено | при новой находке о системе |
| `WORKFLOW.md` | как мы работаем | при новом правиле |

Смешивать их нельзя. «Кап 30 сцен не обоснован в коде» — это CONTEXT. «Поднять кап
осмысленно» — это TASKS. «Параметр, принимаемый API без ошибки, не обязан работать» —
это WORKFLOW. Одна находка часто даёт запись во все три, и это нормально.

Между сессиями память живёт здесь, а не в переписке: новый чат начинается с чтения
этих файлов.

# Часть 1. TASKS.md

## Что обязательно

Одна строка на задачу, чекбокс, жирный заголовок:

```markdown
- [ ] **Короткий заголовок задачи.** [Δ12] Пояснение в свободной форме.
  Продолжение — с отступом в два пробела, сколько нужно строк.
```

Обязательны ровно три вещи:

1. `- [ ]` или `- [x]` в начале строки, без отступа;
2. заголовок жирным — по нему считается идентификатор задачи;
3. подробности с отступом, если они есть.

Всё остальное свободно. Таблицы, списки, ссылки на коммиты, цитаты логов — как удобно.

## Разделы

Разделы — это `##` заголовки. Название произвольное, приоритет считывается по нему:

| в названии есть | приоритет |
|---|---|
| «критич» | критично |
| «заплан», «ближайш» | ближайшее |
| «закрыт» | закрыто |
| что угодно ещё | бэклог |

В разделе «Закрыто» чекбоксы не нужны — пункты считаются закрытыми по факту раздела.

## Статусы

Считаются автоматически:

- `- [x]` → **закрыто**;
- в теле есть `✅` → **в работе** (часть сделана, задача не закрыта);
- в теле есть `⏸️` или «отложено» → **ждёт**;
- иначе → **к работе**.

Если автоматика ошибается, поставьте явно — явное всегда сильнее:

```markdown
- [ ] **Заголовок.** <!-- status: review -->
```

Допустимые значения: `todo`, `in-progress`, `review`, `blocked`, `done`.

## Маркеры

Смысл закреплён, менять нельзя — на них держится дашборд:

- `✅` — часть работы сделана. Писать, что именно и каким коммитом.
- `❌` — **гипотеза опровергнута фактом.** Собирается в отдельный реестр «Опровергнуто»,
  чтобы отменённая идея не вернулась в работу через месяц. Никогда не удалять такие
  строки при уборке файла — это и есть накопленное знание.
- `⚠️` — предупреждение: подводный камень, ограничение, риск.
- `🔴` — критично, даже если раздел некритичный. Поднимает приоритет.
- `⭐` — важное по мнению владельца.

## Кто исполнитель

Задача помечается «только владелец» автоматически, если в тексте есть «руками
владельца», «решение владельца», «не автоматизируется», «юрист» и подобное.
Явная пометка сильнее:

```markdown
- [ ] **Заголовок.** <!-- owner: owner -->    ← только человек
- [ ] **Заголовок.** <!-- owner: agent -->    ← агент может сделать сам
```

Это разделение — половина ценности дашборда: оно отвечает на вопрос «что отдать
агенту прямо сейчас, а что придётся делать самому».

## Идентификаторы

Проставлять руками не нужно. ID считается из заголовка и не меняется, пока не изменён
заголовок. Если заголовок правится, а ссылку надо сохранить — закрепить ID явно:

```markdown
- [ ] **Новый заголовок.** [#T-014]
```

# Часть 2. CONTEXT.md

Знание о системе: архитектура, поставщики, цены, замеры, инварианты, опровергнутые
версии. То, на что ссылаются задачи словами «детали в CONTEXT».

## Что агент дописывает сюда

- **Найденное ограничение поставщика или движка.** Не «попробовали, не вышло»,
  а что именно не поддерживается и чем это доказано.
- **Замер.** Число с условиями, при которых оно получено, и датой.
- **Опровергнутую версию** — с пометкой `❌` и объяснением, чем опровергнута.
- **Новый инвариант** — в раздел «Важные инварианты (не сломать)».

## Как дописывать

В конец соответствующего раздела, с пометкой дельты и датой. Существующие
формулировки не переписывать: если факт устарел, старая строка помечается `❌`
с объяснением, а новая пишется рядом. История ошибок в этом файле ценнее аккуратности.

Числа без условий получения не дописывать вовсе — они хуже отсутствия числа.

# Часть 3. WORKFLOW.md

Правила процесса, накопительно и пронумерованно. Задачи и разборы ссылаются на них
по номеру: «правило 47», «правило 54».

## Номер присваивает владелец, не агент

Номер — это ссылка. Если агент присвоит его сам, два правила рано или поздно получат
один номер, и все ссылки на него станут двусмысленными.

Поэтому агент дописывает **только** в раздел «Кандидаты в правила», без номеров:

```markdown
## Кандидаты в правила (номер присваивает владелец при сведении)

- **Короткая формулировка правила.** Случай, из которого оно выведено: что сделали,
  что получили, чем это кончилось. Без случая правило не принимается.
```

Владелец при сведении переносит кандидата в основной список и даёт номер.
Дашборд показывает счётчик кандидатов — когда их накопилось три-четыре,
сведение назрело.

## Что считается правилом

Правило выводится из случая, который уже стоил времени или денег. Общие соображения
о том, как хорошо бы работать, правилами не являются и в файл не попадают.

# Часть 4. Что агент делает в конце работы

Обязательная часть, без неё схема не работает.

1. **Обновить `TASKS.md`:** статус сделанного, коммиты в теле пункта, новые задачи
   и блокеры, найденные по ходу. Опровергнутое пометить `❌` с объяснением, что именно
   и чем опровергнуто.
2. **Дописать `CONTEXT.md`,** если по ходу выяснился факт о системе: ограничение,
   замер, поведение поставщика, новый инвариант.
3. **Дописать кандидата в `WORKFLOW.md`,** если случай тянет на правило. Без номера.
4. **Ничего не удалять из истории.** Закрытая задача переезжает в раздел «Закрыто»
   одной строкой сути с хешем коммита, а не исчезает.
5. **Не переписывать чужие формулировки** ради красоты. Файлы ведёт владелец,
   агент дописывает.
6. **Собрать `handoff.md`** в корне проекта (перезаписывается каждый раз):

```markdown
# Отчёт: <дата и время>

## Что сделано
Коротко, по пунктам, с ID задач и хешами коммитов.

## Что не получилось
Что пробовал, почему не вышло, что предлагаю дальше.

## Изменения в файлах состояния
TASKS:    добавлено <ID>, закрыто <ID>, опровергнуто <ID и суть>
CONTEXT:  <раздел и суть дописки, либо «без изменений»>
WORKFLOW: <кандидат в правила, либо «без изменений»>

## Открытые вопросы владельцу
Решения, которые агент принять не может.
```

`handoff.md` — то, что владелец копирует в чат для ревью. Он заменяет пересказ
руками и держит контекст в одном месте.

# Чего делать нельзя

- Удалять пункты с `❌` — это защита от повторной траты сил.
- Присваивать номера правилам.
- Менять смысл маркеров.
- Переписывать файл целиком без явной команды владельца. Точечная дописка —
  обязательна каждый раз, перегенерация — только по команде.
- Заводить параллельный трекер задач в другом файле.
- Помечать задачу закрытой без живой проверки, если в задаче написано,
  что проверка нужна.
