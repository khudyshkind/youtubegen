## ЧТО ЭТО ЗА ПРОДУКТ

Lefiro (ранее YouTubeGen) — сервис генерации faceless-видео для YouTube по текстовому запросу: тема → сценарий → озвучка → субтитры → иллюстрации → видео → SEO. Плюс аналитика каналов и ниш. Домен **lefiro.co**. Интерфейс — русский и английский, генерация — 28 языков.

Продукт коммерческий, на живых платежах с 22–23.07.2026. Маржа продукта ≈63% (из дельты №6, не пересчитывалась). Оператор — ИП Худышкин Денис Владимирович.

Предыстория остаётся в силе: до него семь реальных внешних пользователей зарегистрировались, потратили часть стартовых кредитов и не вернулись, **все семеро пришли со своим текстом** (`topic = 'Свой текст'`) и ни один не заказал генерацию по теме. Первый платящий, в отличие от них, дошёл дальше картинок — заказал SEO и превью. Подробности — в разделе «Текущее состояние».

- **Видео-рендер:** отдельный **video-server** на **Railway** (Node + ffmpeg + Whisper). Один процесс на всё: рендер, кроны, Telegram-бот, вебхуки. Сам пишет `projects.video_url`. Deploy Watch Paths включают `video-server/**` и `knowledge/**`. Все обращения к Supabase — сырым fetch через `sbHeaders()` под `SUPABASE_SERVICE_ROLE_KEY` (17 точек).

Картинки + аудио → Supabase Storage (`images` публичный, `audio` приватный signed URL). Старые видео на Backblaze B2 (`videos.lefiro.co`); B2 держит temp/клипы для VGF-пайплайна. Пути: Supabase `{userId}/{projectId}/...`, B2/R2 `users/{userId}/{projectId}/...`.
- **Бэкапы БД:** ежедневно 03:00 UTC в `youtubegen-db-backups`, дата/статус в `bot_settings`, видно в админке.
- **Мониторинг:** Sentry (2 проекта) + Telegram-алерты. UptimeRobot — HTTP-монитор на `/health` video-server, 5 мин, email-алерт. ✅ Δ9: UptimeRobot и Railway-алерты сработали живьём при падении прода — доставка подтверждена.
- **Почта:** Resend (`lefiro.co` verified, FROM `Lefiro <noreply@lefiro.co>`). Custom SMTP на Resend закрыл лимит Supabase 2 письма/час.

### ⚠️ Ограничения инструментов диагностики (Δ9, кровью оплачено)

- **Логи Vercel на Hobby живут 1 час.**
- **Поиск в дашборде логов Vercel НЕ ищет по тексту сообщения.** Запрос по `SUMMARY` вернул строку, где этого слова нет. Отсутствие строк при фильтре **ничего не доказывает**. Рабочий способ: найти любую строку нужного запроса, кликнуть по ней и открыть панель запроса целиком (все строки одного `requestId`).
- Выгрузка логов постраничная: `page=2`, `page=4` в URL — нужная строка может быть на другой странице.
- `vercel ls` и `vercel inspect` **не печатают SHA коммита**. Доказывать деплой ими нельзя (см. правило 33/51).

### Prompt caching (Δ9) — НЕ РАБОТАЕТ на роуте иллюстраций

- В логах **всегда `cache_read:0`**, при любых прогонах, включая повторные на том же проекте и стиле.
- **Порог кэширования зависит от версии модели.** Для **Claude Haiku 4.5 минимум 4 096 токенов** (2 048 — это Haiku 3 и 3.5; 1 024 — Sonnet; для Claude Opus 5 — 512). Проверено по документации, а не по памяти.
- Системные промпты роута: `SCENES_SYSTEM_PROMPT_PHOTO` ≈1 250 токенов, `SCENES_SYSTEM_PROMPT_ILLUSTRATION` ≈2 450 токенов (ОЦЕНКА по символам). **Оба ниже порога 4 096 → кэш не создавался никогда.**
- Вторая причина (вторичная): чанки Claude запускаются через `Promise.all` параллельно, а запись в кэш становится доступна только после начала первого ответа. Внутри одного запроса кэш не сработает в принципе.
- `cache_control: {type:'ephemeral'}` стоит только на system-блоке (`images/route.ts:446` и `:623`); user-сообщение содержит тему, стиль, персонажей и текст сцен — оно уникально всегда и кэшироваться не может.
- В логах печатается только `cache_read_input_tokens`; **`cache_creation_input_tokens` не логируется нигде** — половина картины невидима.
- **Раздувать промпт до 4 096 токенов ради кэша не рекомендуется** (правило 28: жёсткие длинные директивы → паттерны и галлюцинации). Экономия на Haiku мала: системный промпт 2 450 из 2 786 токенов входа самой дешёвой модели.
- **Script-route (сценарий, Sonnet/Opus) — `cache_control: ephemeral` стоит (`script/route.ts:497`), но кеш не создаётся:**
  - `buildSystemPrompt()` возвращает **≈220–450 токенов** — ниже порога 1 024 (Sonnet 4.6) и 512 (Opus 5).
  - **Причина низкого объёма:** план секций (~500–650 токенов, одинаковый во всех N вызовах) лежит в user-сообщении (`buildSectionUserMessage`, строки 365–373), а не в system. Если перенести `sections.map(...)` в system → total ≈720–1 100 токенов → порог 1 024 Sonnet пройдён для 6+ секций.
  - **Параллельный запуск (`runParallelGuarded`, Promise.all):** все N вызовов уходят одновременно; кеш записывается только с первым ответом, остальные N−1 уже в полёте. Кеш реально помогает только retry-вызовам и повторным прогонам в течение 5 мин.
  - **Потенциал при фиксе:** 8 секций, 1 write + 7 reads на ≈1 024-токенный system-блок → $0.006 vs $0.025 без кеша (−76% на system-части; итоговая экономия ≈$0.015–0.020 за прогон).
- **Bot AI consultant (`runConsultant`, строки 894–925 video-server/index.js) — ✅ [2026-08-10] `cache_control: ephemeral` добавлен:**
  - `consultantSystem()` = `lefiroKB` + ~150 слов инструкций (KB первым — порядок для кеша корректен).
  - Факты: `lefiroKB` = **26 844 символа ≈ 6 700 токенов**, порог Haiku 4.5 (4 096) пройден.
  - KB читается **один раз при старте** (`readFileSync`, строка 105, module-level), хранится в `lefiroKB`. На каждое сообщение не перечитывается. 21 строка "[ai-consultant] KB loaded" в логах = 21 рестарт/деплой процесса, не зацикливание.
  - Экономия: 6 700 tok × $0.80/M = $0.00536/вызов → cache read: $0.000536/вызов. Первый вызов за 5 мин пишет кеш, все последующие — читают (−90%).

**Симптом:** в сценарии есть герои с именами, на иллюстрациях они выглядят каждый раз по-разному.

**Механизм цел — проверено разведкой, а не предположено.** Извлечение профилей существует в обоих рантаймах: `extractCharacters` (`images/route.ts:94`) и `imgExtractCharacters` (`video-server/index.js:5333`), максимум 4 персонажа, при ошибке `[]`. Раздел CHARACTER CONSISTENCY RULES в системных промптах написан грамотно и начинается с условия «If CHARACTER PROFILES are provided».

**Настоящая причина найдена по фактическим промптам из `scene_images`** (промпты там сохраняются — это позволило разобраться без единого нового прогона):

- **Профиль был пуст по содержанию.** Haiku возвращала `Alexey, adult male human, travel content creator, average build, casual appearance suitable for YouTube hosting` — ни возраста, ни волос, ни лица, ни одежды. Копировать дословно было нечего. Причина: `descriptionTask` просил «visual description covering **species**/color/features» — формулировка писалась под ролики о животных и для них работает отлично (бабочка: `flat orange body, black and white patterned wings, thin antennae`), а для человека даёт честный ответ о виде.
- **Verbatim-копирование не выполнялось.** Профиль подставлялся один раз, в сцене введения персонажа; дальше шло голое имя: сцена 8 — `fresh determined Alexey`, сцена 9 — `Alexey's distinctive personal branding`. Движок получал слово «Alexey» и рисовал случайного человека.

**Что сделано (коммит `7776312`):**
1. `descriptionTask` переписан в обоих рантаймах и в обеих ветках `styleConfig.illustrative`. Требование: 15–35 слов, обязательные визуальные якоря (для людей — примерный возраст, цвет и длина волос, форма причёски, растительность на лице или явное «no beard», тон кожи, цвет глаз, характерная одежда с цветом; для животных — вид, окрас, узор, размер, две-три характерные части), **явный запрет** формулировок `average build`, `casual appearance`, `adult male human`, `ordinary`, `typical`, `generic`. Ветвление по `illustrative` сохранено: для рисованных стилей якоря описываются как плоские формы.
2. Добавлена механическая подстановка кодом: `injectCharacterProfiles` (`route.ts:153`) и `imgInjectCharacterProfiles` (`index.js:5383`), вызовы в четырёх местах (`route.ts:377`, `:567`, `index.js:5505`, `:5650`). Границы имени — Unicode-lookaround `(?<![\p{L}\p{N}_])имя(?![\p{L}\p{N}_])` с флагами `iu` (первая версия использовала `\b`, который с кириллицей не работает — правило 74).

### Secret Slider — движок иллюстраций (Δ10)

**Где доступен (обновлено Δ11):** инструмент «Иллюстрации» (`/tools/illustrations`) — **синхронно**, кап 15, и **студия, шаг иллюстраций** — **асинхронно, через `image_jobs`, без капа**. **Как устроен вызов** (`images/route.ts`, функция `generateImagesSecretSlider`):
- **Только `mode=visual`, `multipart/form-data`, без файлов.** Текстовый JSON-режим не годится: в нём нет параметра `aspect_ratio` и на выходе 1024×1024. Визуальный режим без референсов даёт то же самое плюс управление пропорцией, стоит столько же и работает не медленнее.
- **Один POST на весь батч.** Поштучные вызовы невозможны: у ключа лимит в одну активную задачу, поштучно батч из 30 занял бы >400 с. Поэтому в роуте отдельная ветка **до** цикла по сценам, а не внутри него.
- Авторизация — заголовок **`X-API-Key`**, не `Authorization: Bearer`. Ключ — `SECRETSLIDER_API_KEY` через `env()`, заведён в Vercel.
- `image_urls` приходят **относительными** путями (`/media/task_results/...`) — origin подставляется на нашей стороне; `status_url`/`download_url` отдаются по `http://` и не используются.
- Выдача **1376×768** (соотношение 1,7917, а не 16:9 = 1,7778). Ресайз не делается: конвейер video-server и так приводит любой размер к 1280×720 через `VF_SCALE = 'scale=1280:720,setsar=1'` — жёстко, без сохранения пропорций (там же `gpt_mini` 1536×1024 сжимается на 17%, и это признано приемлемым). В инструменте файл отдаётся пользователю в нативном разрешении.
- **Стиль передаётся только нашим `fluxSuffix`** в теле промпта. Поле `style` их API (107 значений в 5 категориях) намеренно не передаётся — два указания стиля подрались бы.
- Кап **15** картинок за вызов (сервер + клиентские `max`/клэмп). Обоснован комментарием в коде.
- Бюджет времени: `270 000 мс − (сейчас − старт запроса) − 3500 мс × число промптов`; при остатке < 30 000 мс задача **не создаётся вовсе** — иначе платим за результат, который заведомо не успеем забрать. 270 000 = `maxDuration` 300 с минус 30 с на отработку `catch`/`finally`.
- Сторож перед POST: `GET /api/v2/tasks/active`; при занятом слоте — ошибка `SS_BUSY` → код `BUSY_SECRETSLIDER` → человеческое сообщение с числом секунд. Сбой самого сторожа не блокирует генерацию.

| **референсное изображение** | ❌ **не поддерживается** (тест без `mode=visual` и без именованных полей) ⚠️ **перепроверить**: в OpenAPI есть `mode=visual` с полями `subject_image`, `scene_image`, `style_image` — они не тестировались |
| `system_prompt`, `negative_prompt` | ❌ нет |
| сила влияния референса (`strength`/`denoise`/`image_strength`/`weight`) | ❌ нет ни в OpenAPI, ни в ответах валидации |

**Как доказано отсутствие референса.** Перебор семи имён поля (`image`, `images`, `reference`, `reference_image`, `init_image`, `file`, `files`) дал **идентичную** ошибку `missing_prompt` — то есть неизвестные файловые поля просто игнорируются, и определить имя по валидации нельзя. Контрольный тест: референс-гравюра (сюжет — карманные часы), промпт `a red double-decker bus on a city street` без единого слова о манере, SHA256 промпта совпадает побайтово в обоих вызовах. Результаты с файлом и без файла не отличаются по манере, домен результата в обоих случаях `secretslider.com`. **Файл принимается парсером и отбрасывается сервером.**

⚠️ Первый заход этой разведки был непригоден: сюжет промпта совпадал с сюжетом референса, поэтому сходство результатов ничего не доказывало. Урок — при проверке переноса манеры сюжет обязан быть заведомо чужим.

**Дополнительные факты (OpenAPI-аудит + тест отмены, 2026-08-17):**

- **`POST /api/v2/task/{task_id}/cancel` для PROCESSING** — срабатывает, но с большой задержкой. Немедленный ответ: HTTP 200, `refunded_credits=0`, `canceled_subtasks=0`, `cancel_requested_count=2`, слот остался 1/1 — только ставит флаг `cancel_requested=True`. Реальная остановка воркера происходит через `SubTask.finalize_by_images` спустя часы. **Факт (задача 63294, 2026-08-17):** через несколько часов после вызова cancel — `status=canceled`, воркер успел сгенерировать 2 изображения до прерывания, 2 кредита возвращены (баланс 1283→1285).
- **Принудительной остановки нет.** В OpenAPI-спецификации 21 операция — ни одна не прерывает задачу в статусе PROCESSING. Освободить слот самостоятельно нельзя.
- **Файлы результатов истекают у поставщика через 3 дня.**
- **Лимит запросов:** 60 запросов/мин подтверждено API; `rate_limit_per_day: 0` в ответе API против 500 в документации — расхождение не выяснено.
- **`total_requests` и `last_request_at`** считают только генерирующие вызовы (`POST /generate`), не опросы статуса (`GET /task/{id}`).
- **Параметр `style` API** — не влияет на визуальный результат; стиль задаётся суффиксом промпта (`fluxSuffix`). Проверено на 8 изображениях (anime/photorealism/default/none при одном промпте): разрешение **1376×768 px** одинаковое, визуальная манера неотличима. Параметр API принимается (HTTP 202), варьирует только время генерации: 59 с (default, задача 63589) — 974 с (anime, задача 63628) — 1450 с (photorealism, задача 63568). Мы намеренно не передаём `style` в продакшне. **`estimated_remaining_seconds` систематически завышен:** poll #1 → photorealism 16 072 с при факте 1450 с (11×); default 1996 с при факте 59 с (34×). Убывает ~1 с/с от завышенного значения; возможен временный рост (задача 63568, poll #7: 15 770 → 16 959).
- **Ротация ключей мгновенная**, без grace-периода: первый запрос на старый ключ → 401.
- **15 эндпоинтов работают, но отсутствуют в OpenAPI-спецификации** (21 задокументированная операция — неполный список): `generate-prompts`, `tasks`, `user-styles`, `generate-video`, `generate-preview`, `preview-variants`, `regenerate-image`, `generate-variation`, `task/{id}/download`.
- **Вебхук-приёмник подключён к генерации** — `POST /webhooks/secretslider` на Railway, HMAC-SHA256. `webhook_url` и `webhook_secret` передаются при постановке задачи в SS. Webhook сигнализирует активному poll-циклу (`ssWebhookSignals` Map), тот пропускает следующий sleep и немедленно перепрашивает SS API — вся финализация (upload, кредиты, project) остаётся в одном месте. Идемпотентность через `ssProcessedEventIds` Map (event_id → timestamp, чистится раз в 2 ч). Опрос сохранён как fallback.

**Вывод для превью:** движок не годится. Нет ни одного из рычагов, которыми сокращается число попыток, а именно попытки, а не цена единицы, составляют затратную часть.

### Асинхронный пайплайн генерации иллюстраций (Δ11)

**Зачем:** синхронный роут на Vercel имеет жёсткий потолок 300 с. Secret Slider в него не влезает (ночью 5 картинок — таймаут за 200 с), а длинные проекты не влезают на любом движке. Задача построена по образцу уже работающих `video_jobs` и `audio_jobs` — это не новая архитектура, а третий тип задач в существующей колее.

**Таблица `image_jobs`** (создана 29.07 в боевой Supabase, 20 колонок): `id`, `project_id`, `user_id`, `engine`, `status` (`pending|processing|completed|failed`), `progress`, `script`, `topic`, `duration_sec`, `image_count`, `image_interval`, `image_style`, `custom_style`, `scene_images` (jsonb), `credits_charged`, `credits_refunded_at`, `error_message`, `created_at`, `updated_at`, `completed_at`. Индексы по `status`, `user_id`, `project_id`, `created_at`. `grant all to service_role`. RLS нет — таблица служебная, ходит только сервисный ключ.
✅ **Δ12: добавлена 21-я колонка `provider_task_id text` (nullable)** — id задачи на стороне поставщика, пишется сразу после её создания, до начала опроса. До этого задача, брошенная рестартом Railway или вотчдогом, была невосстановима в принципе: картинки у поставщика есть, деньги уплачены, а ручки нет. Подтверждено живьём: `[images-async] provider task id: 53388`.

**Цепочка:**
1. `Step5Images.handleGenerate` → при `engine === 'secretslider'` уходит в `handleGenerateAsync` (развилка одна, `Step5Images.tsx:375`);
2. `POST /api/generate/images-async` (Vercel) — аутентификация, **проверка достаточности кредитов без списания**, вызов Railway, возврат `job_id`;
3. `POST /generate-images` (video-server, `x-api-secret`) — создаёт запись, запускает `processImageJob` через `setImmediate`, сразу отвечает;
4. клиент опрашивает `/api/generate/images-async/status` раз в 5 с, тот проксирует `GET /image-status/:jobId`;
5. при `completed` Vercel-прокси пишет `scene_images` в `projects`.

**Деньги (важно):** списание **поштучное, после успешной заливки картинки в Storage** — тот же принцип, что в синхронном пути. Порядок строго: заливка → сохранение URL → `deduct_credits` → инкремент `credits_charged`. Первая версия правки списывала всю сумму вперёд и при провале возвращала её целиком, включая уже сгенерированное; переделано на ревью.

**Остановка по нехватке баланса:** `deduct_credits` при нехватке возвращает **HTTP 200 с `{success:false}`** (не ошибку!). При этом цикл **прерывается**: уже оплаченные картинки остаются у пользователя и записываются в проект, неоплаченная в `paidImages` не попадает, задача помечается `failed` с текстом «Недостаточно кредитов — сгенерировано N из M», который доходит до интерфейса. Возврат по оплаченным не делается — они честно получены.

**Отказоустойчивость:** `recoverOrphanedImageJobs()` при старте контейнера (переживает отсутствие таблицы — ошибка ловится, старт продолжается), вотчдог каждые 10 мин, идемпотентный возврат `refundImageJobCredits` через `credits_refunded_at IS NULL`. **Задача не подхватывается после рестарта Railway — помечается `failed` с возвратом.** Деплой посреди чужой генерации прерывает её.

### ⚠️ Δ12: таймаут асинхронного пути переработан (коммит `9cbb359`)

**Инцидент.** Задача `53362` упала с `[secretslider] task timed out (budget=466s)` — а по факту **отработала у поставщика полностью**: уведомление от Secret Slider пришло владельцу уже после нашей пометки `failed`. Картинки сгенерированы, деньги списаны (списание у них происходит в момент постановки задачи, правило 64), результат выброшен.

**Причина — правило 67 второй раз на том же движке.** Пре-флайт-бюджет `270 000 мс − прошедшее − 3500 × N` и внутренний дедлайн существовали из-за `maxDuration=300` на Vercel. В асинхронный путь на Railway они переехали вместе с обоснованием, которого там нет: **ножа платформы на Railway не существует**, процесс живёт сколько нужно, задача живёт в `image_jobs` и переживает закрытие вкладки.

**Что стало:**
- пре-флайт-отказ по бюджету в асинхронном пути снят; в синхронном `images/route.ts` он остаётся и обоснован (`270_000`, отказ при < `30_000`);
- потолок опроса — **`IMAGES_ASYNC_POLL_MAX_MIN`, дефолт 30 мин** (переменная на Railway не заведена, работает дефолт). Это предохранитель от вечно висящей задачи, а не транспортное ограничение;
- **перед пометкой `failed` выполняется последний запрос статуса** — если задача завершилась в промежутке, результат забирается штатно (`RECOVERED`). Это ключевая правка: именно этого шага не хватало в инциденте;
- `WATCHDOG_IMAGES_TIMEOUT_MIN` поднят **15 → 45** с комментарием о связи: при потолке опроса 30 мин вотчдог на 15-й минуте убил бы живую задачу и сделал возврат, воспроизведя ту же потерю другим механизмом. **Порог вотчдога обязан быть заведомо больше потолка опроса**;
- `partial_success` убран из условий успеха и в цикле, и в финальной проверке — успех только `completed` при полном совпадении количества (инвариант правила 65);
- текст ошибки честный: «Генерация не завершилась в отведённое время. Кредиты за неполученные изображения не списаны». Первая версия правки поставила в `throw` успокоительное «генерация продолжается, можно закрыть вкладку» — то есть при фактическом провале пользователь ждал бы картинок, которых не будет. ⚠️ **Отдельного поля для промежуточного сообщения в `image_jobs` нет** (`status`, `progress`, `error_message`, `scene_images`), поэтому «движок загружен, ждём» показать сейчас негде;
- удалены мёртвые `ssBudgetMs`, `uploadReserveMs`, `requestStartMs` — после снятия бюджета они не влияли ни на что, но тащили константу `600_000` («generous deadline 10 min»), то есть то же транспортное ограничение под другим числом (правило 76);
- добавлены замеры: `[secretslider] task start: prompts=N poll_max=Xs`, `task done: task=ID prompts=N duration=Xs polls=K`, `task NOT done: … waited=Xs last_status=… images=…`. `last_status` берётся из финального запроса, при его недоступности — из последнего удачного опроса, поэтому диагностика переживает обрыв связи с поставщиком.

## Архитектура загрузки файлов (upload)

На каждом шаге добавлены кнопки «Загрузить» и «Пропустить».

**Схема загрузки:**
1. Client → `POST /api/upload/sign` → получает `{ signed_url, access_url }` ⚠️ Δ13: расходится с кодом — для `type=tool_audio` `/upload/sign` больше не возвращает `access_url` (фикс SHA 442b63f, см. ERROR_LOG 2026-07-22)
2. Client → `PUT signed_url` с телом файла (напрямую в Supabase Storage, минуя Vercel 4.5MB limit)
3. `access_url` сохраняется в store (для аудио — signed read URL на 1 час; для изображений — public URL)

**Audio bucket** (private): возвращает signed read URL через `createSignedUrl(path, 3600)`
**Images bucket** (public): возвращает public URL через `getPublicUrl(path)`

**Шаги:**
- Step2: FileReader.readAsText(.txt) → setScript()
- Step3: signed upload → setAudioUrl(access_url)  — кредиты не списываются
- Step4: FileReader.readAsText(.srt) → parseSrt() → setSubtitleBlocks()
- Step5: до 20 файлов, каждый через свой signed URL, scene_index = i+1

## Архитектура публикации в Telegram-канал (video-server/index.js, Δ13)

### Целевой канал
`CHANNEL_ID = env('TELEGRAM_CHANNEL_ID')` (index.js:96) — задаётся переменной Railway.
`publishToChannel(text, imageUrl)` (index.js:911) использует его жёстко, выбора цели нет.
`channelPostLink(res)` формирует ссылку с захардкоженным именем: `https://t.me/lefiro_channel/${msgId}` (index.js:927).

### Три потока публикации
Все три заканчиваются вызовом `publishToChannel`:

1. **Ручной пост** (`✍️ Написать пост` → тема → `generateAndHandle`) — index.js:2216–2219, 2173.
   `generateAndHandle` (index.js:1523): генерирует текст + картинку, затем либо `publishToChannel` сразу
   (если `config.autoPublish=true`), либо `showPreview` с inline-кнопками (Опубликовать/Перегенерировать/Отклонить).
   Callback `publish` → `publishToChannel` (index.js:1662).

2. **Мониторинг** (RSS + Claude): `pendingMonitorPost = { post, source, url, score, topic }` (index.js:1411).
   Кнопки `mon_pub/mon_skip/mon_edit/mon_regen` (index.js:1413+).
   Callback `mon_pub` → `publishToChannel(pendingMonitorPost.post)` (index.js:1746).

3. **Деплой** (polling Vercel каждые 30 мин, cron index.js:3591):
   `checkVercelDeploy()` (index.js:3524) → GET Vercel API v6, сравнивает `last_deployment_id` из `bot_settings`.
   При новом деплое берёт `latest.meta?.githubCommitMessage`, генерирует пост через Haiku.
   Если `autoPublish=false` → `pendingDeployPost = { text, commitMessage, deployUrl }` (index.js:3575),
   callback `dep_pub` → `publishToChannel(pendingDeployPost.text)` (index.js:1732).
   ⚠️ Задержка до 30 минут. Бот не знает о Railway-деплоях — только Vercel.

### safeSendMessage и message_thread_id
`safeSendMessage(chatId, text, options)` (index.js:793):
```
const { parse_mode, reply_markup, ...rest } = options
const params = { chat_id, text, ...rest }
```
`message_thread_id` не деструктурируется, попадёт в `...rest` и уйдёт в `tgApi` без изменений кода.
`tgSendPhoto(chatId, buf, caption, extra)` (index.js:743) тоже пробрасывает все поля `extra` в FormData.

### bot_settings — структура
`key text PK, value text NOT NULL, updated_at timestamptz` (schema.sql:576–580). Плоское KV.
`getSetting(key)` / `setSetting(key, value)` (index.js:384–397) — единственный интерфейс.
Маппинг «тема → thread_id» при ≤3 фиксированных темах: добавить ключи `tg_group_id`, `thread_updates`, `thread_releases` и т.п. Если тем произвольно много — отдельная таблица.
