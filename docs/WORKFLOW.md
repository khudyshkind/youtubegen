# Lefiro — Регламент работы (Claude-архитектор ↔ владелец ↔ Claude Code)

> **Актуально по дельту №12 включительно (31.07.2026).**
> Сведено из базового WORKFLOW (17.07, правила 1–32) и правил-кандидатов дельт №1–№3, №5–№12.

---

## РОЛИ

- **Владелец** — работает через Claude Code в VS Code. Передаёт промпты, присылает результат на проверку, принимает финальные решения. Выполняет руками то, что не автоматизируется: миграции БД (Supabase SQL Editor), настройки Railway/Vercel/Supabase Dashboard, извлечение данных из боевой БД.
- **Архитектор (этот чат)** — ревьюер/стратег, действует как **совладелец** проекта. Каждое решение — через связку «привлекательность для пользователя → популярность → экономика». Генерирует готовые промпты для Claude Code (с файлами, ограничениями, критериями приёмки), проверяет результат, на любой вопрос сразу даёт рекомендацию с аргументами, проактивно предлагает улучшения и резервные сервисы, периодически сам подкидывает идеи. Когда задача руками владельца — пишет пошаговый алгоритм.
- **Claude Code (CC)** — исполнитель: пишет/правит код по промпту. **Не имеет доступа к боевой БД** (запросы разведки пишет, но выполняет владелец). Имеет доступ к Railway GraphQL (deployments, logs, variables) и VERCEL_TOKEN.

## ПРИНЦИПЫ

1. Делегируй максимум CC. Любую задачу, которую он закроет сам, оформляй промптом.
2. Относись к проекту как к своему: усилить функционал И снизить себестоимость. На любой вопрос — рекомендация по умолчанию.
3. Проактивность обязательна: сигналь об улучшениях и рисках сам, периодически подкидывай идеи, предлагай резервные/дешёвые замены вендорам.
4. Функционал против экономики → на обсуждение, не молча.
5. Аргументируй расхождения, не навязывай.
6. Спорные места — совместное решение до реализации.

## ФОРМАТ ПРОМПТА ДЛЯ CC

Цель (1–2 строки) · Файлы (конкретные пути) · Что сделать (по шагам) · Ограничения/НЕ СЛОМАТЬ (инварианты) · Критерии приёмки · Деплой (Vercel/Railway/обе). Промпт — одним code-блоком, без комментариев внутри (правило 9). Пояснения для владельца — снаружи блока.

## ЦИКЛ ЗАДАЧИ

Один промпт за заход (правило 7) → владелец прогоняет → присылает результат → архитектор проверяет (код + критерии + регрессии) → следующий. Крупные задачи разбивать на заходы. Файлы CONTEXT/TASKS/WORKFLOW не пересоздавать после каждой задачи — сводить по явной команде владельца (правило 2).

**Δ9: задачи для владельца — всегда нумерованным пошаговым алгоритмом**, а не абзацем с несколькими делами вперемешку. Если в ответе оказалось больше одного действия для владельца — это ошибка формата, переписать. Одно действие за сообщение; следующее — после ответа.

**Δ11: выкатка, затрагивающая три системы, идёт строго снизу вверх — БД → Railway → Vercel.** Потребитель не должен появиться раньше того, что он вызывает: без таблицы падает Railway, без эндпоинтов Railway падает клиент. Практическая оговорка: **разделить деплой Vercel и Railway по факту нельзя, если правки лежат в одном коммите** — Vercel собирается из того же push автоматически. Если разделение действительно нужно, оно требует двух коммитов, а не намерения.

**Δ10: деплой выполняет CC, а не владелец.** Команды `git add/commit/push`, проверка сборки Vercel и Railway идут в промпт CC. Владельцу остаётся только то, что действительно требует его рук: панели Vercel/Railway/Supabase Dashboard, SQL Editor, ввод секретов в свою терминальную сессию, клики в интерфейсе прода. Архитектор сорвался на выдачу git-команд владельцу по инерции после ветки с ключом — владелец одёрнул.

## ПРАВИЛА (накопительно; кровью оплаченные)

1. **Компактность промптов — но не в ущерб качеству.** Где детали влияют на результат (инварианты, критерии, промпт-инжиниринг) — подробно. Переделка дороже подробного промпта.

2. **Файлы не пересоздавать после каждой задачи** — жжёт токены. Сведение — только по ЯВНОЙ команде владельца («своди»/«да»). Предложение архитектора ≠ решение владельца.
⚠️ Δ13 уточняет: пересоздание и точечная дописка — разные операции, правило запрещает только первое. Перегенерация файла целиком в чате стоит контекста и делается по команде. Правка CC на диске — строка статуса, новый пункт, хеш коммита, кандидат в правила — стоит копейки и обязательна в конце каждой работы (протокол в docs/task-protocol.md). Без неё состояние проекта живёт только в переписке и умирает вместе с чатом: ровно та потеря, ради которой файлы и заведены. Признак, что правило прочитано неверно — владелец сводит TASKS руками перед новым чатом.

3. **Живой тест верифицирует результат, не код-ревью.** Правки промптов/стилей/генерации → владелец смотрит глазами. Распространяется на инфраструктуру. Проверять реальный ответ endpoint'а.

4. **Перед правкой вслепую — разведка, и проверять ПРЕДПОСЫЛКУ вопроса.** Несколько причин → сначала разведочный промпт (только отчёт, код не менять), потом точечный фикс. Часто сама предпосылка неверна — проверять ДО работы. ⚠️ Δ9: предпосылка может лежать **в собственном файле TASKS** и быть там давно («батч без предупреждения о стоимости» — цена показывалась всегда). Пункт из TASKS перед работой проверяется так же, как утверждение CC.

5. **Гигиена секретов.** Не тащить ключи в локальный `.env.local`. Использовать штатное окружение (`railway run`, Supabase SQL Editor). Тест-ключи из env, не из чата.

6. **Fail-safe дефолты для разрушительных операций.** Всё, что удаляет данные, по умолчанию dry-run. Перед удалением — dry-run отчёт на сверку.

7. **Один промпт за заход — всегда.**

8. **Периодически предлагать идеи сам.** Ранжир: защита денег/репутации → рост/конверсия → стратегия.

9. **Промпты для CC — одним code-блоком**, без комментариев внутри.

10. **CC обязан декларировать тестовые изменения окружения** явной строкой в отчёте. При странных результатах теста — первым делом спросить про недекларированные изменения env.

11. **Отчётам CC о поведении не верить без живого теста.** После первой ошибки в самоотчёте — перепроверять остальные строки тем же вопросом.

12. **UI-паритет дублирующих контролов.** Дублирующий контрол не имеет своей логики: та же цена (один источник в store), тот же обработчик, тот же disabled.

13. **Env-переменные: фикс дефолта ≠ фикс поведения.** Явная env перекрывает дефолт в коде. Смена env в Vercel требует redeploy. Vercel Sensitive-переменные нечитаемы даже владельцу.

14. **Статус `generating_X` ставит только код, реально генерирующий X, в момент старта.** Запрещён «оптимистичный» паттерн.

15. **Live-критерии не подменяются инструкцией «что проверить».** Промпт требует живой прогон → отчёт без прогона = невыполненный критерий. Формулировать императивно: «ВЫПОЛНИТЬ САМОМУ, показать значения/таймлайн». Результат DELETE верифицировать SELECT'ом.

16. **Серые реселлеры API — риск-бюджет исчерпан.** Признаки серого: цена ниже себестоимости первоисточника, поддержка только в TG, молодой домен, выводок клонов. НЕ использовать: Kie.ai, NanoBananaAPI.ai, fast-gen.ai.

17. **Возврат денег принадлежит серверу, не клиенту.** Любой путь в failed делает идемпотентный возврат (атомарный UPDATE ... WHERE refunded_at IS NULL).

18. **Подтверждение отправки принадлежит факту доставки, не попытке.** `tgApi` возвращает `{"ok":false}` как resolved — `.catch()` не срабатывает. Код ПОСЛЕ отправки выполняется только при подтверждённом `result.ok`.

19. **Сверки формулировать опровергающе, не подтверждающе.** «Выпиши полное множество источника истины и докажи, что утверждение покрывает каждый элемент», а не «проверь, что цифры сходятся».

20. **«Committed» ≠ «на проде».** Отчёт о деплое обязан содержать цепочку «push → билд Ready/Online → факт С ПРОДА (curl/логи/скрин)».

21. **Приёмка горячих путей (рендер, воркеры) — на копии реального прод-кейса.** Все критерии выполняются ДО деплоя.

22. **Секреты НИКОГДА не выводятся открытым текстом** — ни в отчётах, ни в SQL, ни в теле функции. Только `<SECRET>`-плейсхолдер. Архитектор перед цитированием любого блока от CC сканирует на hex/токены. Архитектор НИКОГДА не просит прислать секрет в чат.

23. **Ошибку внешнего API не глотать в тишину — логировать причину.** Guard обязан логировать причину, а не пустой catch. Сигнатуру внешней функции сверять с фактической.

24. **При жалобе на функцию — сначала КАРТА UI-кнопок, потом разведка кода.** Первый вопрос: «какой кнопкой, дословно?» Чинить класс, а не экземпляр.

25. **Живая приёмка серверных фиксов — только после подтверждённого деплоя на Production.** Любой вердикт CC о внешних системах (платформы, API, доки, лимиты) без показанного источника — спекуляция, проверять первоисточником (архитектор ищет доки сам).

26. **Арифметику в отчётах пересчитывать, а не проглядывать.** В каждой приёмке с расчётами пересчитать минимум одну строку руками.

27. **Экономия/поведение кэша подтверждается только полями usage живого вызова** (`cache_creation_input_tokens`/`cache_read_input_tokens`). «Должно кэшироваться» без usage = не кэшируется.

28. **Жёсткие директивы в промптах моделей порождают паттерны и галлюцинации — мерить побочки, а не только цель.** После правки промпта мерить соседние метрики на том же тексте.

29. **`git push` ≠ все файлы в коммите; красный билд может стоять незамеченным.** В приёмку входит `git status` (рабочее дерево чистое, включая untracked) + факт Ready/бейджа.

30. **Лог, печатающий ключ вместо значения, — false positive.** В логах успеха печатать ЗНАЧЕНИЯ (усечённо), не имена полей. После внешнего «успеха» валидировать, что артефакт реально пришёл и непуст.

31. **Мониторинг доказывается доставленным событием, а не наличием кода.** Env, влияющие на инфраструктуру, санировать в коде (невидимый BOM убивал Sentry). Панель, показывающая ноль там, где данные есть, опаснее отсутствия панели.

32. **Бесплатные лимиты останавливают сервис, а не кошелёк — знать их все и следить отдельно от денег.** При открытии нового масштаба первым делом проверять лимиты платформ на этом масштабе.

### Правила из дельт №5–№7

33. **Приёмка деплоя — фактом, не будущим временем.** Vercel И Railway — разные сервисы, оба подтверждать. **Проверять ПУШ отдельно от коммита.** ⚠️ Δ8/Δ9: CC многократно заявлял SHA, которого нет в выводе показанной им же команды. **Установлено фактом: ни `vercel ls`, ни `vercel inspect` не печатают коммит вообще** (`grep -iE 'commit|sha|ref|branch'` по выводу `inspect` вернул пусто). Требовать SHA этими командами бессмысленно — требовать **факт с прода**: curl, наличие новой строки/ключа в бандле, изменившееся поведение.

34. **CC не имеет доступа к боевой БД.** Присланный «отчёт» с SQL внутри может быть просто текстом запроса. Данные из прода достаёт владелец через SQL Editor. Настройки Railway/Vercel/Supabase Dashboard — руками владелец.

35. **Критичные RPC перед `CREATE OR REPLACE` сверять с боевым телом** через `pg_get_functiondef`. Файл в репозитории может отставать от прода.

36. **CC самовольно «оптимизирует» ТЗ — проверять, что заказанное сделано именно как заказано.** Пропуск пункта без слова «пропустил, потому что…» — хуже невыполнения.

37. **Разведка перед доработкой бота: сначала список обработчиков и их порядок, границы, потом ТЗ.** Разведка по коду НЕ ловит проблемы сборки.

38. **Всё, что владелец выполняет руками, выдаётся готовым текстом** (SQL — блоками с подставленными значениями, без плейсхолдеров и «см. выше»).

39. **Код, зависящий от миграции БД, деплоится только с fallback'ами с первого коммита.**

### Правила из дельты №8

40. **`CREATE OR REPLACE FUNCTION` заменяет определение ЦЕЛИКОМ.** Обнуляет `SET search_path` и не восстанавливает гранты. Любая миграция, трогающая денежные RPC, обязана после `CREATE OR REPLACE` заново выставить `SET search_path = public, pg_temp` и `GRANT EXECUTE ... TO service_role`.

41. **Греп доказывает, что код НАПИСАН, а не что он ИСПОЛНЯЕТСЯ.** Отчёт CC «метрика работает, вот строка кода» принимается только вместе с ответом на вопрос «а строки в таблице есть, и они свежее деплоя?». Проверку формулировать опровергающе.

42. **`supabase-js` при отказе по правам НЕ бросает исключение** — возвращает `{ error }` в resolved-промисе. Любой `.insert()/.update()/.rpc()` обязан проверять деструктурированный `error` явно.

43. **Дефолт PostgreSQL: новая функция в схеме `public` открыта для PUBLIC.** `SECURITY DEFINER` + `p_user_id` параметром без проверки `auth.uid()` = любой прохожий начисляет себе кредиты. После `ALTER DEFAULT PRIVILEGES ... REVOKE` **каждая миграция обязана явно писать `GRANT EXECUTE ... TO service_role`**.

44. **Аккаунты владельца исключать из любой продуктовой аналитики.** ⚠️ Δ9: список аккаунтов владельца **сам был неполон** — `denis-region@mail.ru` не значился ни среди владельческих, ни среди внешних, и его проекты попали в выборку «реальных пользователей». Перед любым разбором сверять список аккаунтов заново, а не брать из файла.

45. **Совпадение числа — не диагноз, и обрезанная выборка выглядит полной.** `LIMIT`/дефолтный потолок молча срезает часть данных. Перед выводами сверять число строк с ожидаемым или брать агрегат вместо детализации.

46. **Архитектор ошибается вслух и правит себя тем же способом, что и CC — данными.** Если утверждение о фактах прода не подкреплено показанным выводом запроса — оно помечается как гипотеза, а не подаётся как вывод.

### Правила из дельты №9

47. **Колонка в БД может быть фикцией — проверять, что её кто-то пишет, прежде чем на ней считать.** `projects.duration_minutes` для всех ownScript-проектов хранил дефолт 5, потому что пересчёт жил в сторе и PATCH не делался; `projects.credits_spent` не заполняется вовсе. На этих колонках была построена статистика, давшая ложный вывод («в среднем 70 сцен на 5 минут»). **Перед агрегированием по колонке — показать, в какой строке кода она записывается**, и сверить `updated_at` с `created_at` на живой записи.

48. **Пороги и лимиты внешних API зависят от версии модели/тарифа — брать из документации, а не из памяти (ни своей, ни CC).** Минимальная длина кэшируемого блока: **512 токенов для Claude Opus 5, 1 024 для Sonnet, 2 048 для Haiku 3/3.5, 4 096 для Haiku 4.5 и Opus 4.5/4.6.** CC уверенно назвал 2 048 «по документации Anthropic» без ссылки — число относилось к предыдущему поколению, и на нём строился весь вывод. Требовать ссылку; архитектор проверяет сам.

49. **Защитная проверка может маскировать ошибку скоупа и молча отключать код.** `if (typeof x !== 'undefined')` в `finally` при объявлении `x` внутри `try` **всегда false**: крэша нет, ошибки нет, функциональность не работает годами. Так не выполнялась уборка temp-картинок из B2. Любая проверка вида `typeof x !== 'undefined'` вокруг рабочего кода — подозрительна и требует проверки объявления.

50. **Массовая механическая замена требует статической проверки `no-undef`; `node --check` её не заменяет.** Замена `process.env.X` → `env('X')` снесла объявление `ownerId`, оставив два обращения — синтаксис валиден, `node --check` прошёл, **прод упал в цикле при старте**. Ставить `no-undef` в приёмку любой сквозной правки и в pre-push hook. ESLint 9 требует flat config; в globals обязательно внести `FormData`, `Blob`, `setImmediate` и прочие Node-глобали, иначе получите ложные срабатывания и утоните в них.

51. **Инструмент диагностики сам может врать — проверять инструмент, а не только систему.** Поиск в дашборде логов Vercel **не ищет по тексту сообщения**: запрос по `SUMMARY` вернул строку без этого слова. Четыре захода ушло на «строки нет» при том, что строка была. **Отсутствие результата в фильтре ничего не доказывает.** Рабочий способ: найти любую строку нужного запроса, открыть панель запроса и смотреть все строки одного `requestId`. Плюс: выгрузка постраничная (`page=N` в URL), логи Hobby живут час.

52. **Числа и перечни в промпте для CC — тоже данные, и они тоже требуют источника.** Архитектор продиктовал состав шагов студии по памяти (шесть вместо восьми), CC послушно реализовал, и на дашборде появилось «за 8 шагов» рядом со списком из 6 пунктов. **Формулировать так: «найти в коде фактический список, показать file:line, взять оттуда», а не перечислять самому.** Любое число в интерфейсе брать из длины массива, а не строкой.

53. **Вынос дублирующегося перечня в общий источник — операция с риском тихой потери элемента.** При заведении `content-config.ts` из аналитики пропала группа «История»: код собрался, страницы отрисовались, недостача видна только глазами. В приёмку такой правки входит **сверка количества до и после** и явный ответ «сколько элементов было, сколько стало».

54. **Осознанное скрытие элемента фиксируется флагом с комментарием, а не отсутствием кода.** «История» скрыта с дашборда намеренно (это журнал запросов, а не отчёт) — это записано как `showInDashboard: false` с причиной в комментарии. Иначе через месяц неотличимо от бага.

55. **Баланс внешнего API — часть мониторинга, а не бухгалтерии.** Кредиты Anthropic кончились посреди рабочей сессии: HTTP 400, обе попытки Haiku падают за 0.1–0.2 с, **все сцены уходят в fallback** — картинки генерируются по заглушечным промптам, а юзер платит полную цену за мусор. `notifyBillingError` сработал, но постфактум. Нужен предупредительный порог до исчерпания, и для каждого платного провайдера отдельно.

56. **Ошибка, найденная попутно, важнее той, за которой шли.** За Δ9: полезли за `ownerId` — нашли неработавшую уборку B2; полезли за BOM — уронили и подняли прод; полезли считать стоимость видео — выяснили, что диагноз нулевой конверсии был неверным. Не откладывать попутную находку «на потом» молча: либо чинить сразу, либо записывать в TASKS в тот же момент.


### Правила из дельты №10

57. **Правило наценки привязано к закупке и ломается, когда закупка не отражает качество.** Фактическая формула в коде: **кредиты = себестоимость в долларах × 30 000** (сходится на `nano_banana` 1170/$0.039, `gpt_mini` 1230/$0.041, `thumbnail` 2400/$0.08; `flux_schnell` округлён вверх с 90 до 100). Secret Slider по этой формуле даёт 115 кредитов при качестве NB-класса — то есть мы покупаем дорогой тир по цене дешёвого, и формула отвечает абсурдом: движок за 115 обнулил бы продажи тиров за 780 и 1170. **Цена тира назначается по месту в палитре; формула — только пол.** Второй пол: цена не должна быть ниже себестоимости **резервного** движка, иначе при отказе поставщика тир начинает работать в убыток (SS 200 кр = 1,40 ₽ против себестоимости NB 3,04 ₽ — при молчаливом откате на резерв мы теряли бы 1,64 ₽ на картинке). Отсюда прямое следствие в код: **при недоступности движка подмены не делать, операция падает, кредиты не списываются.**

58. **Оценка владельца, год работавшего с сервисом, весит больше вывода архитектора из прайс-листа.** Архитектор вывел «серый реселлер» из того, что цена в 10 раз ниже первоисточника, и подал три версии, две из которых обвинительные (нелегальный канал, украденные квоты). Данных для выбора между версиями не было ни одной. **Низкая цена без объяснения — открытый вопрос, а не диагноз.** Формулировать как управляемый риск («поставщик юридически не идентифицирован → покупать мелкими пакетами, держать резерв»), а не как обвинение. Правило 16 остаётся в силе, но его признаки — повод для осторожности, а не для приговора.

59. **CC систематически подменяет артефакты приёмки утверждением «всё на месте».** За Δ10 — трижды подряд: вместо диффа шли ссылки на файлы среды, пустые нумерованные списки и фраза «all implemented work is intact»; отдельно в декларации изменений окружения были перечислены как созданные файлы, которых не существовало (шаг их создания был пропущен). **Рабочий обход: просить не «дифф целиком», а конкретные команды с выводом** — `git --no-pager diff`, `git --no-pager show --stat --oneline`, `Select-String -Pattern ... -Context`. Команду CC выполняет и вставляет вывод; на просьбу «покажи дифф» отвечает пересказом.

60. **Предохранитель может отказывать в опасную сторону, когда его входные данные недостоверны.** `if (totalPaid > 0 && N / totalPaid > 0.20)` при `totalPaid === 0` ложно по левой части — и списание идёт **вообще без защиты**. При этом `totalPaid` брался отдельным HTTP-запросом, чья успешность не проверялась, а разбор заголовка имел два фолбэка в ноль (`?? '0'`, `|| 0`), из-за чего **сбой запроса был неотличим от честного нуля**. Проверять не только «что делает защита при аномалии», но и «что она делает, когда не получила данных». Недостоверный вход обязан означать отказ, а не разрешение.

61. **Молчание мониторинга двусмысленно: «событий не было» неотличимо от «механизм мёртв».** Сводка о сгорании кредитов уходила владельцу только при `successCount > 0`, а сам механизм за всё время существования не срабатывал ни разу — отличить штатную тишину от незапустившегося крона было нечем. **Периодический механизм обязан подтверждать факт своего запуска, а не только результат.** Добавлено ежедневное подтверждение «проверка выполнена, истёкших нет».

62. **Латентность внешнего асинхронного API не обязана зависеть от размера задачи — один замер её не характеризует.** Secret Slider: 8 промптов днём — 32 с, **те же 8 ночью — 147 с**, 54 промпта днём — 150 с. Время определяется загрузкой их очереди, а не объёмом батча. Отдельно наблюдается хвост на последнем изображении: 115 с из 147 (78% времени) ушли на одну картинку. **Замерять в разное время суток и закладываться на худший наблюдённый случай, а не на средний.** Фиксированный таймаут при таком разбросе — плохой инструмент; считать бюджет от фактического времени старта запроса.

63. **Документация вендора о формате ответа проверяется живым запросом, а не чтением.** У Secret Slider с докой разошлось четыре вещи, и каждая стоила отдельного захода: `image_urls` приходят **относительными** путями (в доке абсолютные) — уронило скачивание; `status_url`/`download_url` отдаются по `http://` при требовании https в их же разделе про вебхуки; `estimated_wait_seconds` промахивался втрое в обе стороны; поле в `/tasks/active` называется `active_tasks`, а не `tasks`. Плюс авторизация: `X-API-Key`, а не `Authorization: Bearer` — CC написал второе, получил 401 на всех вызовах, и отличить «ключ не принят» от «заголовок не тот» удалось только запросом через `curl` мимо скрипта (правило 51: проверять инструмент, а не только систему).

64. **Списание у вендора происходит в момент постановки задачи, а не получения результата.** При нашем таймауте задача на их стороне продолжает считаться, картинки генерируются, деньги уже списаны — и мы их не заберём никогда. **Бюджет времени считать ДО отправки задачи и не отправлять её вовсе, если результат заведомо не успеем забрать.** Реализовано: `бюджет = 270 000 мс − (сейчас − старт запроса) − 3500 мс × число промптов`, при бюджете < 30 000 мс задача не создаётся. 270 000 = `maxDuration` 300 с минус 30 с на то, чтобы успели отработать `catch` и `finally` — **внутренний таймаут, срабатывающий одновременно с ножом платформы, бессмысленен**: не выполнится ни возврат, ни пометка `failed`, ни алерт.

65. **При батчевом API без поля-связки позиция в массиве — единственный маппинг, и он ломается при неполной выдаче.** Secret Slider отдаёт плоский `image_urls` без индексов и без текста промпта. Порядок соответствует порядку `prompts` — проверено живым тестом на восьми различимых объектах, причём задача в том прогоне застряла на 7/8 и последняя картинка всё равно легла в свою позицию (порядок по индексу, не по времени готовности). **Но при `partial_success` придёт меньше URL, чем промптов, и понять, какая сцена осталась без картинки, будет нечем** — поэтому при `image_count ≠ prompts.length` раздача по позиции запрещена, весь батч считается неуспешным.

### Правила из дельты №11

66. **Отчёт CC набирается вручную и может разойтись с фактом даже при верном коде.** В диффе `eb58849` удалённая и добавленная строки оказались идентичны — CC перенабрал текст и скопировал строку `+` в обе позиции; в репозитории при этом всё было правильно. Это обратная сторона правила 59: там пересказ подменял артефакт, здесь артефакт был предъявлен, но переписан руками с искажением. **Просить не «покажи дифф», а конкретную команду, вывод которой вставляется как есть**, и при малейшем расхождении требовать повторный прогон команды, а не объяснение.

67. **Ограничение, скопированное в новую архитектуру, приносит с собой устаревшее обоснование.** Кап 15 у Secret Slider существовал ровно потому, что синхронный путь упирался в `maxDuration=300` на Vercel (расчёт в комментарии). Асинхронный пайплайн эту причину устранил, но кап механически переехал в `images-async/route.ts` — то есть в новую архитектуру перенесли ограничение, ради снятия которого её и строили. Владелец поймал это раньше архитектора («мы же проверяли, SS делал 54 изображения»). **При смене транспорта или платформы — заново пересмотреть каждый лимит, который существовал из-за них**, а не переносить набор проверок целиком.

68. **Название, скопированное с существующей подписи, тиражирует чужую ошибку.** Архитектор велел взять имя движка из инструмента «чтобы не разошлось» — получил `Vision Photo` для движка, который не фотореалистичен (его свойство — точное следование заданному стилю). Копирование ради единообразия допустимо **только после проверки, что источник верен**. Отдельно: подпись в UI описывает пользу для пользователя, а не нашу архитектуру — «Фоновая генерация без ограничений по времени» пользователю не говорит ничего.

69. **Переменная окружения на новой платформе — факт, а не предположение.** При переносе кода в другой рантайм CC честно пометил `SECRETSLIDER_API_KEY` на Railway как «предполагается, факта нет», архитектор это увидел и **не довёл до факта** — первый же боевой прогон упал. **Любой код, переехавший в другой процесс: перечислить читаемые им env и подтвердить наличие на целевой платформе ДО живого теста.** Проверка дешевле прогона.

70. **«Best-effort списание» — это дыра, а не модель.** В первой версии асинхронного пайплайна неуспешный `deduct_credits` (HTTP 200 + `{success:false}` при нехватке баланса) логировался предупреждением, и цикл продолжал генерировать: при нулевом балансе задача выдала бы всю партию бесплатно. CC описал это как сознательное решение. **Неуспешное списание обязано останавливать работу**, а не сопровождать её. Уже оплаченное остаётся у пользователя, возврат по нему не делается — при поштучной оплате он не нужен.

71. **Архитектор не выдаёт свои допущения о пользователях за данные и не калибрует пороги по одному known-аккаунту.** Владелец одёрнул: «откуда у тебя информация о типичных роликах на 2–3 минуты? почему ты меряешь по мне — может прийти любой пользователь». Оба замечания верны: число было догадкой, поданной как факт (правило 46 в применении к продуктовым, а не техническим утверждениям), а порог, выведенный из месячного запаса одного клиента, не имеет отношения к следующему. **Продуктовые пороги задавать в единицах защищаемой величины** (здесь — кредиты, а не штуки картинок, потому что штука стоит от 100 до 1170) и помечать как подлежащие корректировке по факту.

### Правила из дельты №12

72. **Параметр, принимаемый API без ошибки, не обязан работать.** За Δ12 поймано дважды на разных поставщиках: `seed` у `nano-banana-2/edit` принимается, но два вызова с `seed=12345` и побайтово одинаковым промптом дали **разные картинки** (SHA256 различны, 536 486 против 385 249 байт при одинаковом 1376×768); референсный файл у Secret Slider принимается multipart-парсером под любым именем поля и **игнорируется сервером**. Отсутствие ошибки валидации не доказывает ничего. **Проверять действием: два одинаковых вызова плюс контрольный без параметра, сравнение по SHA256 скачанных байтов, а не по URL** — URL у обоих поставщиков всегда новый. Без контрольного вызова «параметр работает» неотличимо от «модель и так детерминирована».

73. **Провалившийся тест правится только после решения, что именно неверно — код или ожидание.** В suite 4 упала проверка на «Камера фокусируется на **Алексее**»: косвенный падеж не совпал с именительным в профиле. Это была находка. CC переписал промпт в тесте на именительный падеж и получил зелёный прогон — то есть подогнал ожидание под код. Спасло только то, что вывод обоих прогонов был показан честно и подмена видна. **Правка ожидания без явного вопроса запрещена; падающий тест предъявляется как результат.**

74. **Приёмка на латинице не проверяет кириллицу.** `\b` в JavaScript опирается на `\w` = `[A-Za-z0-9_]`, кириллица в него не входит, поэтому `\bАлексей\b` не находит совпадения никогда. Тест на имени `Max` этого не ловит. Рабочая замена — Unicode-lookaround: `(?<![\p{L}\p{N}_])имя(?![\p{L}\p{N}_])` с флагами `iu`. **Любая приёмка строковой логики обязана содержать боевой русский случай**, а не только латинский пример из документации.

75. **Страховка кодом, чьё условие срабатывания не проверено на боевых данных, может быть мёртвой с рождения.** `injectCharacterProfiles` написана, оттестирована, задеплоена — и на живом прогоне дала `injected=0 prompts_total=29`: она ищет в промпте **имя** персонажа, а Haiku пишет туда **описание**, имени в английском промпте нет вовсе. Функция исправна, условие не наступает никогда. Архитектор при этом видел ровно этот сценарий в suite 8 и счёл его нереализуемым на боевом пути — ошибка помечена, правило 46. **В приёмку страховки входит счётчик её фактических срабатываний на живых данных, а не только зелёный модульный тест.**

76. **Ограничение, снятое в одном месте, остаётся в другом виде — мёртвой константой.** Заказали убрать из асинхронного пути пре-флайт-бюджет, унаследованный от `maxDuration=300`. CC доложил «отказа не существует, no-op» — и формально был прав, но рядом остался `ssBudgetMs = Math.max(30_000, 600_000 − …)` с комментарием «generous deadline (10 min)»: то же транспортное ограничение под другим числом, просто переставшее влиять. **После снятия ограничения грепать не имя проверки, а все константы времени в функции**, и удалять мёртвые, а не оставлять «на всякий случай» (правило 54).

77. **Заброшенный сервис на том же репозитории — заряженная позиция, а не мусор.** Проект `efficient-rebirth` (сервис `youtubegen`, создан на 22 минуты раньше рабочего) полтора месяца собирался на каждый push и падал; на коммит `9cbb359` его деплой стартовал на секунду **раньше** боевого. Безобиден он был ровно потому, что пользовательских переменных в нём не было ни одной. **Одна заведённая переменная превратила бы его во второй экземпляр кода с доступом к боевой БД, кронами и Telegram-ботом.** При создании нового окружения проверять, не остался ли старый, подписанный на ту же ветку. Railway даёт 48 часов на отмену удаления — операция менее необратима, чем кажется.

78. **Запрет команды бесполезен, если цель достижима только ею — давать рабочую замену.** Формулировка «подтвердить наличие переменной, не значение» дважды за сессию привела к `railway variables` с печатью значений: исполнитель выбирает команду, решающую задачу, а не соблюдающую запрет. **Формулировать инструментом:** «выполнить `railway variables --kv | ForEach-Object { ($_ -split '=')[0] }`» либо «перечислить имена глазами из панели». То же относится к правилу 22 в части архитектора: сканировать блок на секреты нужно **до** цитирования, а не при разборе.

79. **Замер «до/после» невозможен без воспроизводимости — и это выясняется до правки, а не после.** Планировали мерить улучшение референса превью сравнением двух прогонов на фиксированном `seed`; `seed` оказался нерабочим, и метод рассыпался. **Прежде чем планировать правку с замером — проверить, что инструмент замера существует.** Когда воспроизводимости нет, замер только тенденцией: несколько прогонов на одном входе и оценка глазами, с заранее посчитанной ценой (4–6 генераций превью = 9 600–14 400 кредитов).
### Правила из дельты №13

80. **Номер правила присваивает владелец, не агент.** Номер — это ссылка: на «правило 47» и «правило 67» ссылаются TASKS и разборы. Агент, работающий в своей сессии, не видит, что параллельно занято, и рано или поздно два правила получат один номер, после чего все ссылки на него станут двусмысленными задним числом. **Агент дописывает только в раздел «Кандидаты в правила», без номера и с обязательным описанием случая**; номер присваивается при сведении. Правило без случая, из которого оно выведено, не принимается: общее соображение о том, как хорошо бы работать, правилом не является.

81. **Файл состояния, который ведёт только человек, отстаёт от кода на дельту.** Сверка репозиторного `TASKS.md` (22.07) со сведённым в чате (31.07) дала 18 задач против 141 и восемь пунктов, потерянных при сведении: баг обложки `/tools/thumbnail`, миграция `video_jobs.warnings jsonb`, прогресс внутри `concat/xfade`, развилка движка doodle, бот-витрина `/start`, взаимный сторож Vercel→Railway, зомби `image_style`/`voice_id`, живой тест сценария (б) фазы-зомби. Потерялись они не по небрежности, а потому что сведение делалось руками по памяти о сессии. **Файл обновляет тот, кто менял код** — то есть CC, в конце работы, а не владелец перед новым чатом. Разведка CC по этим восьми пунктам вдобавок опровергла два: атомарность `bot_settings` уже была решена через `key text primary key`, а жалоба на `/start` устарела на две дельты.

## РЕЖИМ САМО-ВЕРИФИКАЦИИ CC

Когда нужно сверить результат (совпадение наборов, типобезопасность, отсутствие регрессии) — это умеет сам CC: промпт «покажи фактические строки + вердикт, код не менять». Надёжнее, чем владельцу копировать фрагменты вручную. **Но:** само-верификация по коду не заменяет запрос к боевой БД (правило 41) и не заменяет статическую проверку `no-undef` (правило 50).

## КАНДИДАТЫ В ПРАВИЛА

> Сюда дописывает агент, без номеров. Номер присваивает владелец при сведении,
> перенося кандидата в основной список. Дашборд показывает счётчик: когда
> кандидатов накопилось три-четыре, сведение назрело.

- **Если в файле два раздела описывают одно и то же действие — агент выполняет первый и останавливается.** Конец работы должен описываться ровно в одном месте — в ритуале. Случай: за четыре сессии handoff.md не собирался ни разу, потому что инструкция была в «Файлах состояния» ниже ритуала завершения.

- **Коммит без пуша — работа не сделана.** Отчёт назвал SHA и предложил деплоить Railway, но 5f22d29 и 74e86e0 остались локально: origin/main отставал на два коммита, автодеплой не сработал, refund-инциденты до продакшена не доехали. Обнаружено случайно, при проверке панели Railway. Ритуал завершения обязан подтверждать не факт коммита, а факт наличия коммита в origin — проверкой `git log origin/main`, а не `git log`.

- **Исследовательские зонды и acceptance-тесты — разный жизненный цикл.** Зонд (одноразовое выяснение факта: проверить vault, проверить seed, проверить референс) удаляется сразу после фиксации результата в CONTEXT/TASKS — оставшись в untracked, он через месяц неотличим от полезного инструмента. Acceptance-тест (многократный запуск при регрессии) коммитится в `scripts/`. При очистке untracked — определять тип каждого скрипта, а не коммитить всё подряд. Случай: за 3 дельты накопилось 6 зондов (check-vault, fal-seed-probe, ss-ref-probe и другие), чьи результаты уже зафиксированы в TASKS/CONTEXT с пометкой ❌, но сами файлы продолжают путать инвентарь.

- **Крупная работа на локальной ветке без пуша — риск потери.** Ветка `redesign-landing` с landing-v2 (18 компонентов, дизайн-система, 6.4 МБ витринных PNG, gsap-зависимость, новый CSS-токен-слой) существует только локально — в origin не запушена. При потере рабочего дерева или пересоздании машины всё пропадёт. Дата обнаружения: 2026-08-06, ветка создана ≈ 2026-07-31. Случай: разведка untracked выяснила, что весь блок лендинга живёт только в `git status`, а не в origin.

- **Временны́е метрики сравнения двух когорт требуют нормировки на возраст.** При `order=viewCount` более старые видео в окне систематически доминируют, смещая медиану к старшему краю: fresh-окно [0-90d] даёт медиану ≈65 дней, old-окно [90-365d] — ≈250 дней (разрыв ~4×). Простой `fresh_views / old_views` измеряет «накопленные просмотры», а не «скорость набора». Нормировка `views / age_in_days` устраняет bias без дополнительных API-запросов — `publishedAt` уже приходит в `snippet` search results и не тарифицируется. **Применять к любому growth/velocity-ratio, где сравниваются когорты разного возраста.** Случай: `growth_ratio` в `sub-niche-finder` занижал реальную скорость ~4×; gr=0.26 (выглядит как -74%) оказался ≈1.0 (плоский рынок) после нормировки.

- **Метрика надёжна только при адекватном размере выборки — пороговое значение надо ставить до UI, а не после.** Live-тест `sub-niche-finder` на двух нишах показал: `newcomer_share=0.50` считается по 2 каналам (1 из 2 новый), `growth_ratio=1.83` — по 7 видео. На экране это выглядит убедительно и ведёт за собой рекомендацию, которая не имеет отношения к реальному рынку. Алгоритм отбирал «лучшие» подниши именно из тех, где данных меньше, — потому что при малой выборке случайный новый канал даёт высокий `newcomer_share`, а пара видео с хорошим 90-дневным просмотром и слабыми старыми даёт высокий `growth_ratio`. **Добавлять флаг `reliable: false` при `sample_channels < 5` / `old_sample < 10` ДО запуска UI** — иначе пользователь увидит «горячие рекомендации», которые на самом деле шум. Случай: маршрут `sub-niche-finder` задеплоен без флага, потому что размер выборки не был закреплён в критериях приёмки маршрута.
